# Testing this extension
This directory contains all the tests for this extension. The `sql` directory holds tests that are written as [SQLLogicTests](https://duckdb.org/dev/sqllogictest/intro.html). DuckDB aims to have most its tests in this format as SQL statements, so for the drex extension, this should probably be the goal too.

The root makefile contains targets to build and run all of these tests. To run the SQLLogicTests:
```bash
make test
```
or
```bash
make test_debug
```

## The mock Drex API

The `prompt_drex_*.test` and `drex_decide.test` files call a mock of Drex's `POST /v1/systemone` and `GET /v1/models`,
`mock/drex_mock.py` (Python 3.10+ standard library only). They skip unless `DREX_MOCK_URL` is set, so the distribution
pipeline, whose tests run in Docker, skips them; `.github/workflows/MockContractTests.yml` runs them.

Run them locally:

```sh
python3 test/mock/drex_mock.py --port 8787 &
export DREX_MOCK_URL=http://127.0.0.1:8787
# for prompt_drex_secret_env.test; a well-formed test key, never a real one
export NACE_API_KEY=nace_sk_mockKeyForDrexContractTests_222222222222222
export NACE_BASE_URL=$DREX_MOCK_URL/ns/secret_env/ok
make test
```

The mock's own checks: `python3 -m unittest discover -s test/mock`. With the `jsonschema` package installed (CI
installs it), they also validate every response against its schema in Drex's `openapi.json`: the subset in
`mock/openapi.json`, or the file `DREX_OPENAPI` names. When Drex's answers or errors change, refresh the subset from
Drex's `main` and update the mock to match:

```sh
python3 test/mock/openapi_subset.py ../drex/openapi.json "$(git -C ../drex rev-parse --short HEAD)"
```

### What the mock does

- **Validation.** It refuses what Drex refuses, ported from `lib/ndm.ts`: a malformed key (401), `instructions` that
  isn't a string, a `noul` with neither instructions nor criteria, images on a model that doesn't read them, more than
  512 questions, and so on (422 with `issues[]`).
- **Answers** are deterministic. A question matching one of `openapi.json`'s documented examples (by type,
  instructions and criteria, whatever its id) gets the documented answer. A `choice` between `red` and `blue` on a
  request with images gets the colour of the image its instructions name (`Image N`, default 1). Anything else: a
  `noul` is 0.75, a `choice` picks its first label (weights n, n-1, ..., 1), a `score` weights its levels 1, 2, ..., n.
- **Scenarios.** A secret's `BASE_URL` of `<mock>/ns/<ns>/<scenario>` picks the behaviour; `<ns>` keeps each test
  file's requests apart. `ok` answers; `401`, `402` and `422` answer with that error; `429-once` and `529-once` refuse
  the first attempt of each body (with `retry-after-ms` 1000 and 2000) and answer the retry; `529-always` never
  answers (`retry-after-ms` 2000), so a row runs out of its 5 attempts and is NULL; `too-long` answers but refuses a
  request over 1,024 tokens (4 bytes of JSON state a token, 258 an image) with Drex's own 422: `Request too long:`
  with issue path `state`, or `""` for a request with images, counted whole as Drex Max counts it; `slow-<ms>`
  answers as `ok`, each `/v1/systemone` request after holding it `<ms>` milliseconds (1 to 60000), so a call's
  requests overlap.
- **OpenRouter.** With `SET http_proxy` pointing at the mock, a request for `https://openrouter.ai/api/<route>` is
  answered as OpenRouter answers it: `GET /v1/models` lists `nace-ai/` models only with
  `output_modalities=decisions`, and `POST /v1/systemone` takes `sk-or-v1-` keys and `nace-ai/` models, refuses with
  400 a question without `instructions` or top-level `images`, and reads images from `state` content parts. Every
  other request through the proxy is served as usual. The mock answers the `CONNECT` itself, with a self-signed
  certificate for `openrouter.ai` that the `openssl` command makes on first use and `<mock>/__fixtures/openrouter.pem`
  serves: a test copies it to a local file for `SET GLOBAL ca_cert_file` (GLOBAL, since the extension's requests read
  the database's settings, not the connection's).
- **Images.** `<mock>/__fixtures/red.png` and `blue.png` are 320 x 320 solid PNGs generated by `mock/pngs.py`. No
  image file is committed.

### The request log

`mock/requests.test_template`, included by each file, defines `drex_reset(ns)` and `drex_requests(ns)`, a table of
the requests the mock received under `ns`:

| Column | |
| --- | --- |
| `seq` | Order of arrival, across all namespaces |
| `open_router` | Whether the request was for `https://openrouter.ai/api`, through the mock as `http_proxy` |
| `scenario`, `method`, `endpoint`, `status` | As requested and answered |
| `retry_after_ms` | The `retry-after-ms` the mock sent, or NULL |
| `authorization_header`, `user_agent`, `x_nace_client`, `idempotency_key`, `content_type`, `http_referer`, `x_openrouter_title` | Request headers, NULL when absent |
| `model`, `model_present` | The body's `model`, and whether it had one |
| `served_model` | The model that answered, for a 200 |
| `state_type`, `state` | The body's `state`: its JSON type (`string`, `object`, ...) and its JSON text |
| `question_count`, `questions` | The questions, as a JSON array of objects with their `id` added, in request order |
| `instructions_present` | Whether every question has `instructions` as a string |
| `image_count`, `image_colours` | The `images`, and the colour (`red`, `blue`, `unknown`) of each, in order |
| `body_sha256`, `body` | The raw body, and its hash |
| `attempt`, `waited_ms` | The how-manyth time this body was sent in this scenario, and the milliseconds since the previous time |
| `in_flight` | The namespace's requests the mock was answering when this one arrived, itself included; its `max` is the peak |
| `received_at` | When the request arrived, in seconds since the Unix epoch |

### Error messages the tests expect

The contract tests check the binder and transport messages. Every message the extension writes starts with the function's name (`prompt_drex: ` or
`drex_decide: `), then:

- More than 512 questions, on any model: `512`.
- Images on a model that doesn't read them: the model and `image`.
- An unknown model: its name. A non-constant argument: `must be a constant` (DuckDB's own message).
- `multiple_choice` or `box`: the argument's name.
- Criteria that are neither a `VARCHAR[]` of labels nor a `STRUCT(label, description)[]`: the argument and the two
  forms (the tests look for the argument and `label`). `noul` labels other than `true` and `false`: the labels found.
  A `score` level with a description: `score levels take no description`.
- Too few or many choices or levels: `2` and `255`. Duplicate labels: `unique` or `duplicate`, and the label. Two of
  `noul`, `choice`, `score`, `questions`: their names.
- 401: Drex's message, without the key. 402: Drex's message and `dashboard/billing`. 422 about the questions or
  model: every issue as `path: message`, in order.
- A 422 about the row (`Request too long:`, or issues only under `state` and `images`) and an image that isn't a PNG,
  JPEG or WebP fail no query: the row is NULL, with the WARNING `a row returned NULL: ` and the reason, never the
  row's content.
- No secret: `No nace secret found` (the secret lookup's message, without the prefix).
- A `BASE_URL` with `http://` to a host other than `localhost`, `127.0.0.1` or `[::1]`: `nace secret: base_url must use
  https:// outside localhost` (the secret's own prefix).

## The transport test

`transport/transport_test.cpp` calls `DrexClient` directly against the mock, so it covers the transport (retries,
errors, headers, the limiter, the 4 MiB limit and OpenRouter's body shape) before `prompt_drex` and `drex_decide` are
bound. `transport/echo_proxy.py` stands in for OpenRouter: the test sets DuckDB's `http_proxy` to it and reads back the
request it received, over a tunnel with the mock's certificate, which the proxy writes for the test's `ca_cert_file`.
After `make`, from the repository root:

```sh
test/transport/run.sh
```

It builds the test against `build/release`, starts the mock and the proxy on ports 8787 and 8788 (`MOCK_PORT`,
`PROXY_PORT`), and takes about 20 seconds, most of it the retry waits.

`BUILD=debug` or `BUILD=reldebug` builds it against that build instead, with its sanitizers.

## The stress test

`stress/stress_test.cpp` covers what the SQLLogicTests can't: interrupting a query (`Connection::Interrupt`) while its
requests are in flight, while rows wait out `retry-after-ms`, a `drex_max_rpm` token or a slot another connection
holds; replacing and dropping the secret while a query runs; closing the database while a query runs; throughput
against the cap; and 100k rows run twice, with memory and thread counts measured. Every check is a hard bound, such as
an interrupted query ending within a second. After `make` or `make debug`, from the repository root:

```sh
test/stress/run.sh            # release, with 100k rows; about 2 minutes
test/stress/run.sh debug      # AddressSanitizer and UBSan, with 10k rows
```

It builds the test against that build, starts the mock on a free port, and takes the scale test's rows from
`DREX_STRESS_ROWS` (0 skips it). `sql/concurrency_*.test` cover the in-flight cap and the RPM bucket in SQL.

## Sanitizers

CI builds release only, so run these before a release, with the mock set up as above. A debug build has
AddressSanitizer and UndefinedBehaviorSanitizer; `THREADSAN=1` gives a ThreadSanitizer build:

```sh
make debug && make test_debug && BUILD=debug test/transport/run.sh
THREADSAN=1 make reldebug
export TSAN_OPTIONS="suppressions=$PWD/duckdb/.sanitizer-thread-suppressions.txt"
make test_reldebug && BUILD=reldebug test/transport/run.sh
```

On macOS, delete `build/*/**/*.duckdb_extension` before rebuilding a build you have run: the kernel keeps an
extension file's old code signature, and kills a test that loads the rewritten file.

## The Python client

`python/test_semantics_python.py` loads the built extension into the `duckdb` Python package with
`allow_unsigned_extensions`, against the mock. The package refuses an extension built for another DuckDB version, and
a local `make release` is a dev version, so build with `OVERRIDE_GIT_DESCRIBE` set to the release in `./duckdb`:

```sh
OVERRIDE_GIT_DESCRIBE=v2.0.0 make release
uv run --no-project --with duckdb==2.0.0 python -m unittest discover -s test/python
```

It skips unless `DREX_MOCK_URL` is set and the build is there. It loads the built httpfs, so it downloads nothing.

## The live tests

`sql/live/prompt_drex_live.test` calls the real Drex API on `drex-v2.0` and `drex-max`, with images. It skips unless
`DREX_LIVE` is set. `.github/workflows/LiveTests.yml` runs it on demand with `NACE_API_KEY` set from the
`NACE_LIVE_API_KEY` Actions secret. These tests send data to the real service and can incur charges.
Run them locally with a dedicated test account:

```sh
python3 test/mock/pngs.py /tmp/drex-fixtures
DREX_LIVE=1 DREX_LIVE_FIXTURES=/tmp/drex-fixtures NACE_API_KEY=... build/release/test/unittest "test/sql/live/*"
```
